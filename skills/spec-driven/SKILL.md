# Spec-Driven Development Framework

This skill enforces a disciplined four-phase flow before writing any code.

**Golden rule: never advance to the next phase without explicit user approval.**

## The Flow

```
User request
      │
      ▼
[PHASE 1] SPEC ──► user approves ──►
[PHASE 2] PLAN ──► user approves ──►
[PHASE 3] CREATE TASKS ──► user approves ──►
[PHASE 4] EXECUTE (one task at a time)
```

## Phase Files

Read the relevant phase file when you reach that phase. Do not load all of them at once.

| Phase | File | When to read |
|-------|------|--------------|
| 1. Spec | `references/spec.md` | At the start, to understand the problem fully |
| 2. Plan | `references/plan.md` | After the spec is approved |
| 3. Create Tasks | `references/create-tasks.md` | After the plan is approved |
| 4. Execute | `references/execute.md` | After the tasks are approved |

## Cross-cutting tools

These are **not phases.** They can be invoked at any point in the flow, independently of each other.

| Tool | File | When to use |
|------|------|-------------|
| Grill | `references/grill.md` | Whenever clarity is missing in any phase — runs a focused interview |
| Context | `references/context.md` | Whenever a new or refined domain term appears — keeps `.spec/CONTEXT.md` up to date |
| Doc | `references/doc.md` | Whenever an important, hard-to-reverse decision is made — records it under `.spec/docs/` |

Grill often produces context updates or docs as outputs, but each tool stands on its own — you can update the glossary or write a doc without grilling, and you can grill without producing either.

## How to invoke

The framework is operated through **slash commands**, one per phase or tool. Each command is designed to run in **its own session** so context stays isolated between phases.

| Command | What it does | Typical input |
|---------|-------------|---------------|
| `/spec <description>` | Phase 1 — writes `.spec/NNN-slug/spec.md` | New feature/change description |
| `/plan <NNN-slug>` | Phase 2 — writes `.spec/NNN-slug/plan.md` | Feature folder with approved spec |
| `/tasks <NNN-slug>` | Phase 3 — creates `.spec/NNN-slug/tasks/TASK-*.md` | Feature folder with approved plan |
| `/execute <NNN-slug> <TASK-NNN>` | Phase 4 — implements one task and stops | Feature folder + task ID |
| `/grill <topic>` | Tool — clarifying interview | Whatever is unclear |
| `/context <term>` | Tool — update glossary | Domain term to add/refine |
| `/doc <decision>` | Tool — record a hard-to-reverse decision | Decision title |

**Recommended pattern: one session per command.** Each command does a pre-check, runs its phase, and hands off with the exact next command to run. Open a fresh session for the next step so the previous phase's context doesn't bleed in. The `.spec/` folder is the shared memory between sessions.

This is enforced by design: every command ends by telling the user the next command to run and refuses to advance further in the same session.

## When to use this skill

Use this framework whenever the user asks to:
- Implement a feature
- Refactor a module or class
- Fix a non-trivial bug (more than a one-line change)
- Do any work that touches multiple files

Do NOT use for: conceptual questions, explaining existing code, or trivial one-line fixes.

## Workspace structure

All artifacts generated by this skill live under `.spec/` at the project root, grouped **by feature**:

```
.spec/
  CONTEXT.md                       ← shared domain glossary (created lazily)
  docs/                            ← shared decision records (created lazily)
    0001-event-sourced-orders.md
  001-user-registration/
    spec.md
    plan.md
    grill.md                       ← (optional) grilling session log
    tasks/
      TASK-001-create-users-table.md
      TASK-002-expose-post-users.md
  002-password-reset/
    spec.md
    plan.md
    tasks/
      ...
```

Rules:
- One folder per feature, named `NNN-descriptive-slug` (zero-padded, sequential).
- Each feature folder contains its own `spec.md`, `plan.md`, and `tasks/` subfolder. `grill.md` is optional.
- `.spec/CONTEXT.md` and `.spec/docs/` are **shared across features** and created lazily — only when the corresponding tool produces them.
- Pick the next feature `NNN` by looking at existing folders under `.spec/` and adding 1. Docs use their own sequence `NNNN` under `.spec/docs/`.
- **`.spec/` is meant to be committed** by default — specs, plans, glossary, and docs are part of the project's history and are reviewable in PRs. The user can `.gitignore` it if they prefer to keep it local.
